在 AI-901 考試綱要裡，Microsoft 使用比較一般性的名稱 Entity Detection；
但在 Azure Language 的正式服務/功能名稱裡，對應的核心功能叫 Named Entity Recognition (NER)。

| 功能 | 正式英文名稱 | 在做什麼？ | 簡單例子 | 考試記法 |
| --- | --- | --- | --- | --- |
| **關鍵片語擷取** | **Key Phrase Extraction** | 從非結構化文字中找出能代表**主要概念、主題或重點**的片語 | 「飯店很乾淨，員工親切，而且離車站很近」→ `飯店`、`員工`、`車站` | **找重點** |
| **實體辨識** | **Named Entity Recognition (NER)**；AI-901 綱要也會寫 **Entity Detection** | 從文字中找出特定**實體（Entity）並分類**，例如人名、地點、組織、日期 | 「Satya Nadella visited Microsoft in Seattle」→ Satya Nadella = **Person**、Microsoft = **Organization**、Seattle = **Location** | **找實體＋分類** |

**Key Phrase Extraction = What is this text about?（找重點）**

**NER = Who / Where / Which organization / When?（找實體）**

| 類型 | 回答的問題 |
| --- | --- |
| **Multiclass** | 這張圖片**最主要是哪一類？** |
| **Multilabel** | 這張圖片**有哪些標籤？** |

判斷口訣：問題只能選一個答案 → 多類別 ｜ 可以同時成立多個答案 → 多標籤。⚠️ 多標籤 ≠ 多類別！多類別是「多個選項選一個」，多標籤是「每個標籤獨立判斷有/沒有」。

| 類型 | 正式英文 | 判斷對象 | 一張圖可有多個類別嗎？ | 可判斷多個物件嗎？ | 有位置資訊嗎？ | 簡單例子 |
| --- | --- | --- | --- | --- | --- | --- |
| **多類別影像分類** | **Multiclass Image Classification** | 整張圖片 | ❌ 最終選 1 類 | ❌ | ❌ | 貓 / 狗 / 鳥三選一 → **Dog** |

LUIS 是 **Language Understanding Intelligent Service**，以前是 Microsoft Azure 用來做 **自然語言理解（NLU）** 的服務。

Microsoft 原本建議 LUIS 使用者移轉到：

> **Conversational Language Understanding (CLU)**
> 

CLU 是 Azure Language 中更新版的自然語言理解功能。Microsoft 官方也直接稱 CLU 為 LUIS 的 updated version。

它的核心工作只有兩件：

> **判斷使用者想做什麼（Intent）**
> 
> 
> **從句子裡抓出重要資訊（Entity）**
> 

Microsoft 官方描述 LUIS 為：對輸入文字預測整體意圖，並擷取重要資訊的自然語言理解元件。

| 名稱 | 正式英文 | 意思 | 例子 |
| --- | --- | --- | --- |
| **語句** | **Utterance** | 使用者實際說／輸入的整句話 | 「幫我訂明天去台北的高鐵」 |
| **意圖** | **Intent** | 使用者想完成什麼事情 | `BookTrainTicket` |
| **實體** | **Entity** | 完成意圖需要的重要資訊 | `明天 = Date`、`台北 = Destination`、`高鐵 = Transport` |

- **Verification** 是 **one-to-one matching**，回答的是「這兩張臉是不是同一個人？」

- **Find Similar** 是從候選人臉中找「外觀相似」的臉，但結果**不一定代表是同一個人**。

**Detect = 有沒有臉 / 在哪裡**

**Attributes = 臉的特徵**

**Identify = 1:N，這個人是誰**

**Verify = 1:1，是不是同一人**

**Find Similar = 找長得像的**

**Group = 把相似臉分群**

### Tagging 到底是什麼？

假設圖片是：

> 一隻狗在草地上跑，背景有房子。
> 

Tagging 可能回：

- `dog`
- `animal`
- `grass`
- `outdoor`
- `building`
- `running`

而且每個 tag 通常還會有一個 **confidence score**。Microsoft 官方範例就是像 `grass`、`outdoor`、`building` 等 tag 加上 confidence。([Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-services/computer-vision/concept-tagging-images?utm_source=chatgpt.com))

所以它回答的是：

> **「這張圖片可以用哪些詞描述？」**
> 

這就是題目說的：

> metadata that summarizes the attributes of the image
>

所以：

> **Tagging = 描述圖片**
> 
> 
> **Categorizing = 把圖片歸類**

{
  "customerName": "...",

  "total": 0,
  "items": [
    {
      "name": "...",

AI 的工作就是：

> 從不同版面的文件中，把內容填進這張答案卷。
>

- `string`
- `number`
- `integer`
- `boolean`
- `date`
- `object`
- `array`

所以可以表示複雜表單和表格。([Microsoft Learn](https://learn.microsoft.com/en-us/rest/api/contentunderstanding/content-analyzers/get?view=rest-contentunderstanding-2025-11-01&utm_source=chatgpt.com))

## 題目裡的「relationships」怎麼理解？

這裡不用想得太複雜。

重點是：

> 不只知道某個值存在，還知道它在你定義的結構裡**屬於哪個欄位、哪個物件、哪筆 repeated entry**。
> 

例如：

```
Product: Mouse
Qty: 3
Price: 500
```

不是只抽出：

> Mouse
> 
> 
> 3
> 
> 500
> 

而是建立：

```json
{
  "Product": "Mouse",
  "Quantity": 3,
  "Price": 500
}
```

如果有很多行，就形成：

```json
"items": [
  {...},
  {...},
  {...}
]
```

所以它強調的是：

> **值 + 結構 + 關係**
> 

而不是只是 OCR 把字讀出來。

### NIST AI RMF 原本的四大 Function

NIST 原始 AI RMF 的正式架構是：

| NIST AI RMF Function | 中文理解 |
| --- | --- |
| **GOVERN** | 建立治理、政策、責任 |
| **MAP** | 了解情境、找出風險 |
| **MEASURE** | 衡量、評估風險 |
| **MANAGE** | 排序、處理與管理風險 |

也就是：

> **Govern → Map → Measure → Manage**
> 

而你這張 AI-901 題目看到的是：

> **Identify → Measure → Mitigate → Operate**
> 

這不是 NIST 原始四個 Function 的逐字名稱，而是 **Microsoft 對 Responsible Generative AI 的實務流程**。Microsoft 官方說，這四個階段和 NIST AI RMF 的 functions **closely correspond**，也就是「高度對應」，不是說兩者名稱完全一樣。([Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/overview?utm_source=chatgpt.com))

所以你筆記最好這樣分：

| NIST AI RMF | Microsoft Responsible Generative AI |
| --- | --- |
| **GOVERN** | 整體治理貫穿流程 |

## 所以這題為什麼選 A？

題目問：

> What is the **first stage** to consider when developing a responsible generative AI solution?
> 

Microsoft 的流程：

```
1. Identify
2. Measure
3. Mitigate
4. Operate
```

所以答案：

> ✅ **Identify potential harms**
> 

意思是開發 GenAI application 前，第一件事情不是先上線，也不是先做 content filter，而是先問：

> 「這個系統可能造成什麼傷害？」
> 

例如你做客服 AI：

可能 harm 包含：

- 提供錯誤資訊
- 產生歧視性回答
- 洩漏個資
- 產生 offensive content
- 使用者過度依賴 AI 建議

先把這些找出來。

之後才：

```
Identify
↓
有哪些 harm？

Measure
↓
這些 harm 多常出現、多嚴重？

Mitigate
↓
Prompt / Guardrails / filters / application logic

Operate
↓
部署、監控、持續管理
```

## Field 和 Repeated Rows 的關係

一張發票可能長這樣：

```
Vendor: ABC Corp                  ← Field
Invoice No: INV001               ← Field
Date: 2026/09/05                 ← Field

Product     Qty   Price           ← ↓
Keyboard     2     100            ← repeated row
Mouse        5      50            ← repeated row
Monitor      2     400            ← repeated row

Total: 1250                      ← Field
```

因此可以記成：

| 類型 | 例子 | JSON 結構 |
| --- | --- | --- |
| **Field** | Vendor、Invoice No、Total | single value |
| **Repeated Rows** | 商品明細 | array of objects |

|  | **Field Extraction** | **Content Extraction** |
| --- | --- | --- |
| 核心目的 | 我要「特定資料」 | 我要「文件內容＋結構」 |
| 是否先定義 schema | ✅ 通常要 | ❌ 不一定 |
| 輸出重點 | Key-value / structured fields | Text + layout elements |
| 表格處理 | 變成你定義的 `LineItems[]` | 保留 rows / columns / cells |
| 例子 | `VendorName = ABC Corp` | 發現某段文字在 Page 1 某區域 |
| 適合 | Business automation | OCR、search、RAG、document understanding |

![image.png](AI-901%20Notes/image%2024.png)

原始圖片：

```
黑色 Nike 跑鞋
```

Content Understanding 可以同時產：

### Markdown

```
A black athletic running shoe with a white sole.
The shoe has a lightweight design suitable for running.
```

→ 放進 **Search Index**

### Structured Fields

```
{
  "ProductCategory":"Shoes",
  "Color":"Black",
  "Style":"Running Shoe"
}
```

其中：

```
ProductCategory
```

可能使用：

> `classify`
> 

---

### Source

```
D(1,120,80,400,300)
```

→ 告訴你結果是從圖片哪個區域 grounding 出來的。

所以三個東西完全不同：

```
Markdown
→ 內容是什麼
→ Search / RAG

Fields
→ 我要的結構化答案
→ JSON / automation

Source
→ 答案從哪裡來
→ grounding / location
```

| Approach | 定義 | 優點 | 缺點 | 適合情境 |
| --- | --- | --- | --- | --- |
| **Exact Label Matching** | 根據特定 label 文字找值，例如 `Total:` | 簡單、固定模板很好用 | Label 改變就容易失敗 | 高度固定的表單 |
| **Fixed Page Coordinates** | 根據固定 x/y 位置取得內容 | 固定模板快速 | Layout 改變就失敗 | 完全固定版型 |
| **Schema-defined Fields & Relationships** | 定義想抽取的欄位、型別、語意與結構 | 可處理 label/layout 變化、複雜與手寫表單 | 需要先設計 schema | **Content Understanding、複雜表單** |

# Schema-defined field 不一樣

你不是告訴模型：

> 找 `"Customer Name:"` 這幾個字。
> 

而是告訴它：

> 我要一個欄位叫 `CustomerName`，它代表「填表人的姓名」。
> 

概念上：

```
{
  "CustomerName": {
    "type":"string",
    "description":"The full name of the customer or applicant"
  }
}
```

於是 AI 可以理解：

```
Customer Name
Name of Applicant
Applicant
Full Name
姓名
```

這些可能都在表達：

> **CustomerName**
> 

所以：

```
不同 label
       ↓
理解語意
       ↓
CustomerName
       ↓
"Steven Yeh"
```

這就是 schema-defined 的優勢。

---

## 最重要的差異

|  | Exact Label Matching | Schema-defined Fields |
| --- | --- | --- |
| 依賴什麼 | **表單上實際寫的 label** | **欄位的語意 / schema** |
| 例子 | 找 `"Invoice No"` | 定義 `InvoiceNumber` |
| Label 改字 | 容易失敗 | 通常仍可理解 |
| 不同版型 | 很脆弱 | ✅ 較適合 |
| 手寫表單 | 較不適合 | ✅ 適合 |
| Visually complex forms | 較不適合 | ✅ 適合 |
| 固定模板 | 可以很有效 | 也可以 |
| 彈性 | 低 | 高 |

# 再舉一個發票例子

你想抓：

```
Invoice Number
Invoice Date
Vendor
Total Amount
```

但是不同公司發票可能：

### 公司 A

```
Invoice #: INV001
Date: 09/05/2026
Supplier: ABC Corp
Total: $500
```

### 公司 B

```
Document Number: INV001
Issued On: 09/05/2026
Seller: ABC Corp
Amount Due: $500
```

### 公司 C

```
發票號碼：INV001
開立日期：2026/09/05
供應商：ABC Corp
應付金額：$500
```

如果你用 **Exact Label Matching**：

```
"Invoice #"
"Date"
"Supplier"
"Total"
```

公司 B、C 很可能抓不到。

但 Schema 可以定義：

```
InvoiceNumber
InvoiceDate
VendorName
TotalAmount
```

AI 的工作是理解：

```
Invoice #
Document Number
發票號碼
      ↓
InvoiceNumber
```

以及：

```
Total
Amount Due
應付金額
      ↓
TotalAmount
```

這就是：

> **Schema-defined = 你定義「我要什麼資料」，不是規定文件一定要怎麼寫。**
>

# 那題目講的 relationships 又是什麼？

`schema-defined fields and relationships`

不只可以定義單一欄位，還可以定義資料之間的結構。

例如一份申請表：

```
Customer
├── Name
├── Phone
└── Address

Products
├── Product 1
│   ├── Name
│   ├── Qty
│   └── Price
└── Product 2
    ├── Name
    ├── Qty
    └── Price
```

你就可以讓 Schema 表達：

```
{
  "Customer": {
    "Name":"...",
    "Phone":"...",
    "Address":"..."
  },
  "Items": [
    {
      "ProductName":"...",
      "Quantity":2,
      "Price":100
    }
  ]
}
```

所以 relationships 可以理解成：

> **欄位彼此的結構關係**
> 

例如：

- Customer 底下有哪些欄位
- 一個 invoice 有很多 line items
- 每個 line item 又有 Product、Quantity、Price

# 為什麼叫 Unified Model Invocation API？

因為 Responses API 不只是「聊天室」。

它想把很多不同使用情境集中在一個介面：

```
Text
Image
Tools
Function calling
Structured output
Multi-turn state
Agents / Foundry capabilities
        ↓
    Responses API
```

Microsoft Foundry 官方目前也把 Responses API描述成「programmatic interface for every model in Microsoft Foundry」。

所以題目特別放：

> **unified model invocation API**
> 

其實就是非常直接的考試 keyword：
